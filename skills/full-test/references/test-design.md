# 从需求生成可执行测试用例

在生成测试计划、手工用例、自动化场景或冒烟范围时读取本文件。只执行现有测试、只整理报告时无需重新设计整套用例。

## 收集足够的上下文

先使用用户已提供的 PRD、验收条件、接口定义、页面地址、代码变更和现有用例。已有信息能回答的问题，不重复询问。

优先确认会改变测试行为的内容：

- 本次功能、版本、目标环境及明确排除项。
- 关键用户、角色、业务路径和高影响变更。
- 可用测试账号、合成数据、执行工具和清理方式。
- 已存在的测试命令、报告目录及项目约定。

缺少地址不妨碍设计用例；缺少预期规则时，不用实现现状代替需求。把待确认项写出来，先完成不依赖该答案的部分。

## 建立需求与用例的对应关系

为需要验证的业务行为分配稳定 ID，例如 `REQ-001`。沿用已有需求编号，不另造一套。

把一条宽泛需求拆成可观察的行为：输入、前置状态、用户动作、系统输出和最终状态。只在拆分能定位失败原因时增加用例。

每条用例使用稳定 ID，例如 `UI-001`、`API-001`、`MANUAL-001`，并引用需求 ID。重跑保持 ID 不变；修改场景含义时说明变化。

| 需求 ID | 可验证行为 | 用例 ID | 覆盖方式 | 未覆盖原因 |
|---|---|---|---|---|
| REQ-001 | 有效测试账号可登录并看到自己的页面 | UI-001、API-001 | UI + API | 无 |
| REQ-002 | 错误凭据不会创建有效会话 | API-002 | API | UI 提示文案待确认 |

这张表服务于发现缺口。小任务可以把需求 ID 直接写进用例，无需再建独立矩阵。

## 按影响选择优先级

| 优先级 | 判断依据 | 常见例子 |
|---|---|---|
| P0 | 核心服务不可用，或存在高影响的数据、权限问题 | 无法登录；跨用户读取敏感数据 |
| P1 | 主要业务路径失败，影响常见操作 | 无法提交订单；保存后数据丢失 |
| P2 | 次要功能、可绕过的分支或较低频操作受影响 | 筛选条件组合；非核心导出 |
| P3 | 影响较小的边缘场景或展示问题 | 不影响理解的布局细节 |

依据项目业务调整上述例子。优先级描述影响，不能代替真实执行结果，也不自动决定一个版本是否可发布。

## 选择有效的测试技术

围绕本次需求选择有区分力的场景，避免对所有字段机械排列组合。

- **等价类：** 有效输入、无效格式、缺失值和不支持的类型各选代表。
- **边界值：** 已知限制为 `n` 时检查相邻边界；限制未知时先记录待确认，不能编造最大长度。
- **异常路径：** 验证用户能否理解错误、状态是否保持一致、重试是否产生重复结果。
- **权限：** 无会话、有效会话、低权限角色和资源所有者的行为应与明确的权限规则对应。
- **状态转换：** 检查允许与禁止的转换，以及失败操作是否留下错误状态。
- **数据一致性：** 保存、刷新、重新查询后验证状态；读取到旧值时区分异步约定与真实缺陷。
- **回归：** 覆盖变更影响的相邻行为，复用已有测试，避免为相同断言重复建套件。

接口用例还应区分请求有效性、状态码、响应结构和业务约束。UI 用例应断言用户能看到的结果，而非仅确认元素存在。

## 用例最小结构

| 字段 | 内容 |
|---|---|
| ID / 需求 ID | 稳定用例编号及对应需求 |
| 标题 / 类型 / 优先级 | 具体行为；UI、API 或手工；P0–P3 |
| 前置条件 / 数据 | 可重建的状态、测试角色、合成数据 |
| 步骤 | 足以独立执行的操作；自动化时可映射到脚本 |
| 预期结果 | 可观察的断言及其依据 |
| 清理 | 本用例创建了什么，以及如何恢复 |
| 状态 / 证据 | 设计阶段为 `NOT_RUN`；执行后记录观察与证据 |

不要在“预期结果”中只写“正常”“成功”或“符合要求”。应写清结果，例如“返回的记录 ID 与本次创建 ID 相同”，但必须有需求或契约支持这一预期。

可以用下面的 Markdown 形式交付少量用例；需要协作筛选时再输出 CSV 或 JSON。

```text
ID: UI-001
需求: REQ-001
标题: 有效账号登录后进入个人首页
优先级: P0
前置条件: 存在可用的测试账号；未登录
步骤: 打开登录页 → 填写测试凭据 → 提交
预期: 出现需求指定的个人首页标识，且账号身份与测试账号一致
清理: 退出测试会话
状态: NOT_RUN
待确认: 个人首页的稳定业务标识
```

此示例仍有待确认项，因此不能直接宣称已经具备可执行的完整断言。

## 形成最小冒烟集

选择能快速证明应用基本可用的关键路径：入口加载、核心内容可见、主要操作可完成、结果状态可核实。按产品决定是否包括登录、保存、查询或结账。

每条冒烟用例应能暴露明显构建或部署问题，并提供具体失败位置。把复杂组合、压力测试和大量边界移到后续回归集。

冒烟失败时停止依赖该前置条件的后续检查，标为 `BLOCKED`；可独立执行的检查继续进行。不要让早期失败导致整套用例被错误标为通过。

## 设计与执行分开记录

| 状态 | 使用条件 |
|---|---|
| PASS | 实际执行且有证据支持所有预期断言 |
| FAIL | 实际执行，观察结果与有依据的预期不符 |
| BLOCKED | 已要求执行，但缺少环境、账号、工具或前置状态 |
| SKIPPED | 本轮明确决定不执行，并记录原因 |
| NOT_RUN | 仅完成设计或尚未执行 |

只生成脚本、阅读源代码、看到构建成功、得到一张未检查的截图，均不能把业务用例标为 `PASS`。

证据应能回答“运行了什么、看到什么、为何判定”。保存实际命令、退出码、时间、关键日志和相关截图；不保存明文凭据、会话文件或无关用户数据。

重跑保留原失败及新结果。若一次通过不能排除间歇失败，记录重试情况与限制，不把失败历史从报告中抹去。

## 交付前检查

检查关键需求是否有用例，预期是否有来源，数据是否可获得，步骤是否独立可重复，优先级是否符合业务影响。

交付与当前任务相称的内容：范围、用例、覆盖缺口和待确认项；执行过再附实际结果。对于环境未就绪的场景，说明最小解除阻碍条件，继续完成其余已授权工作。
